> **Update:** the move described below never actually happened in this codebase — the pages were still in `app/(seller)/catalogue/` behind the seller login. They now really live at `app/admin/(protected)/(sales)/catalogues/` and read through a staff-only API. See CUSTOM_SELLERS.md.

# Catalogues route — now wired to your real schema

## What was actually wrong

`app/admin/(sales)/catalogues/page.tsx` and `[catalogueId]/page.tsx` were
still the old mock version (in-memory `ADMIN_CATALOGUES` array, seller
propose → admin approve/reject workflow).

But a *correct*, already-real-Supabase-backed rewrite of both pages
existed in your zip — just saved under the wrong path:
`app/(seller)/catalogue/page.tsx` and `app/(seller)/catalogue/[catalogueId]/page.tsx`
(both files even have `// app/admin/(sales)/catalogues/...` as their own
header comment, confirming that's where they were meant to live). The
seller portal's real product page already lives at
`app/(seller)/(dashboard)/products/page.tsx`, so the stray `catalogue/`
folder under `(seller)` was just a misplaced duplicate, not a second
seller-facing feature.

## What changed

1. **Moved** the real pages into place:
   - `app/admin/(sales)/catalogues/page.tsx` — now queries `products`
     joined with `sellers(name, platform_slug)` directly via
     `lib/supabase/client.ts`. Read-mostly list (search by product/seller
     name), since sellers now manage their own products directly and
     there's no approval step anymore.
   - `app/admin/(sales)/catalogues/[catalogueId]/page.tsx` — shows the
     full product record, and lets admin edit exactly one thing:
     **margin %** (Wishdrop's markup on top of the seller's cost price),
     plus toggle active/hidden and hide-from-listings (soft delete).
2. **Deleted** the now-empty `app/(seller)/catalogue/` folder and the
   dead mock file `data/catalogues/data.ts` (confirmed nothing else in
   the codebase imported it).
3. **Added** `app/api/admin/catalogues/[catalogueId]/route.ts`
   (GET/PATCH/DELETE) — this is what the detail page's margin-save and
   hide-from-listings actions call. It's the piece that was missing
   entirely; without it the moved page would have compiled but every
   save/delete click would 404.
   - `PATCH` only accepts `{ marginPercent }` and `{ active }` — never a
     raw `price`, so price is always recomputed server-side from
     `cost_price * (1 + margin/100)`, which is exactly the "never let
     someone type a final price directly" rule called out in the route
     spec doc.
   - `DELETE` sets `active = false` rather than deleting the row — soft
     delete only, per the spec. Updated the button copy from "Delete...
     can't be undone" to "Hide from listings" since it's reversible.
4. **Replaced** `lib/supabase/types.ts`'s `Database = any` placeholder
   with real Row/Insert/Update types generated by hand from the schema
   you pasted (all 44 `public.*` tables). This isn't a substitute for the
   real `supabase gen types` output (enum values aren't known from a
   dump, so those columns are typed as `string`), but every `.from(...)`
   call in the repo was checked against it and all match.

## Worth knowing / still open

- **No approval workflow anymore.** The old mock had a whole
  seller-proposes → admin-approves flow (`pendingChange`,
  `submitChangeRequest`, etc). The real schema has no supporting table
  for that (no `pending_changes` / `change_requests` table), and the
  rewritten page's own comment confirms this was a deliberate product
  decision, not an oversight: sellers edit their own products directly,
  no review step. If you actually still want an approval step, that
  needs a new table + this route rebuilt around it — flag if that's the
  case, because it changes the shape of both pages again.
- **Not role-gated yet.** Like the existing `admin/sellers` routes, the
  new `admin/catalogues/[catalogueId]` route only checks "is someone
  logged in," not "is this a Manager/Sales & Purchase account." Same
  caveat that's already written into `app/api/admin/sellers/**`.
- **The `Add product` / `catalogues/new` modal from the original route
  spec doesn't exist in this version** — again, deliberate per the
  rewritten page's comment, since creation now happens on the seller's
  side. If admin still needs to create a catalogue entry on a seller's
  behalf, that's a feature to build, not a bug to fix.
